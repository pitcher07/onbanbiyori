## 1. エグゼクティブサマリー

### 1.1 コンセプト

**人材の才能を見抜き、育て方と組み合わせで未来を変える、歴史蓄積型の音楽事務所育成シミュレーション。**

プレイヤーは音楽事務所を運営する立場で、多様な人材を発掘する。候補者をバンドに限定せず、能力・適性を見ながらソロ、バンド、アイドル、ユニット等の活動形態を選択し、育成する。アーティストの能力や育成の成果は楽曲制作などの活動に反映され、活躍や実績が事務所の歴史として積み重なる。

上記は合意事項を統合したコンセプト文であり、正式なゲーム名や宣伝文句は未定。

## 2. ユーザーが求める体験

### 2.1 着想の背景

ユーザーは、サカつく・栄冠ナイン等の育成系ゲームが好きである。ドラクエ系RPGも挙げているが、今回の方向性は音楽事務所育成ゲームに絞られている。参考作品の個別システムをそのまま採用することは決まっていない。

重視するのは、手塩にかけ、時には贔屓して育てた存在が活躍し、歴史に名を残す体験である。能力を見て適性を考える遊びを重視し、単なる外見や人気の収集だけで終わらない方向を望んでいる。

### 2.2 体験上の柱

以下はユーザーの志向と合意事項を、設計の評価軸として整理したもの。

1. **発見する楽しさ**：候補者の能力・個性から、育てたい人物を見つける。
2. **育てる手応え**：才能だけで結果が決まらず、方針や扱い方で成長が変わる。
3. **適性を生かす自由**：活動形態やメンバー構成を変え、その人に合う道を探せる。
4. **活躍を見届ける喜び**：能力が楽曲や実績に結びつく。
5. **歴史が残る満足感**：一度の成功を消費して終わらず、作品と人物の歩みが蓄積する。
6. **短時間で関われる手軽さ**：毎回大量の細かい操作を要求しない。

### 2.3 設計を判断する際の問い

新機能を追加するときは、「発掘・育成・愛着・歴史のどれを強めるか」「操作負担に見合うか」「能力と結果のつながりが理解できるか」で評価する。これは本資料の設計提案であり、追加機能を自動的に承認するルールではない。

## 4. 基本ゲームループ

以下の順序は、決定済みの要素をつないだ**論理上の整理**である。画面遷移、ターン内の厳密な処理順、毎ターン全工程を実行することまで合意したものではない。

1. オーディションや場所指定スカウトで候補者と出会う。
2. 能力・適性・個性を見て、迎える人材や育成対象を選ぶ。
3. 活動形態、メンバー構成、育成方針を決める。
4. 時間を進め、成長と活動の結果を受け取る。
5. 重要イベントに対応し、必要に応じて方針や編成を見直す。
6. 能力・パラメータを反映した楽曲が自動的に制作される。
7. 活躍やランキング、蓄積した実績を確認する。
8. 新たな発掘と育成に戻り、事務所の歴史を延ばす。

加入の契約・費用、デビュー手続き、リリースの操作、ライブの実行方法は未決定である。ループを描くためにそれらの制度を確定したことにしない。

## 5. システム別の設計・仕様

### 5.1 プレイヤーの立場と事務所

**決定**：音楽事務所側として、多様な人材を発掘・育成・プロデュースする。

プロデュースには、人材の適性を見て活動形態や組み合わせを考える意味がある。楽曲ごとの細かな制作指示を初期版の必須操作にする意味ではない。

**未決定**：資金、収支、スタッフ、施設、契約、所属上限、事務所ランク、経営難・破綻、初期状態。題材が「事務所」であることだけを理由に、これらの経営管理要素をすべて初期実装へ追加しない。

### 5.2 人材発掘

**決定**：定期オーディションと場所指定スカウトを併用する。

| 手段 | 合意された役割の骨格 | 既出案・未決定事項 |
|---|---|---|
| 定期オーディション | 定期的に候補者と出会える | 幅広い候補を出す案。開催間隔、人数、候補者分布は未決定 |
| 場所指定スカウト | プレイヤーが場所を選んで人材を探す | 場所ごとに出会いやすい適性を変える案。確率や費用は未決定 |

**既出の場所案（採用確定ではない）**：ライブハウス＝演奏・作曲、ダンススクール＝ダンス・スター性、路上ライブ＝歌唱・表現、SNS＝作曲・独創性。

これらは発掘場所の例であり、ライブ運営やSNS運用ゲームを初期搭載することを意味しない。また「スター性」「独創性」は説明用の語として登場しており、正式パラメータとして採用されたとは限らない。

**未決定**：候補者の生成方法、採用／見送り、同じ候補者との再会、発掘時の情報量、希少人材、スカウト失敗、費用・所要時間。

### 5.3 能力・才能・個性

**決定**：能力重視。才能に加え、育て方によって結果が大きく変わる方式を採用する。

**既出の構造案**：現在能力、隠れた潜在能力、個性・固有特性という三層で人材を表す。この構造は採用した方向性の説明に含まれていたが、各フィールドや数式まで確定したものではない。

| 層 | 既出の説明 | 詳細の扱い |
|---|---|---|
| 現在能力 | 現時点で発揮できる力 | 数値範囲、表示方法、初期分布は未決定 |
| 潜在能力 | 成長率・限界値等。育成で徐々に判明する案 | 固定上限の有無、開示条件、育成による変化は未決定 |
| 個性・固有特性 | 育成や活動の違いを生む性質 | 種類、数、効果、獲得・変化方法は未決定 |

**既出の能力候補**：歌唱力、演奏力、作曲力、ダンス、表現力、カリスマ。

**既出の個性候補**：天才肌、努力家、本番に強い、スランプになりやすい、カリスマ性。

能力候補の「カリスマ」と個性候補の「カリスマ性」は重複し得るため、正式な属性設計時に整理する。両方を独立した確定能力として扱わない。

**設計上の論点**：潜在能力を固定上限として実装する場合も、「育て方で大きく変わる」という決定を形骸化させない。育成の影響先を、成長速度・伸びる能力・得意分野・組み合わせなどのどこに置くかは未決定。

### 5.4 育成

**決定**：方針設定＋時間経過＋重要イベントのバランス型。

プレイヤーの意思決定と、時間が進むことによる成長の両方を使う。すべてを細かく手動で指示する方式、すべてを放置する方式のいずれにも固定しない。

**未決定**：育成方針の選択肢、個人単位かグループ単位か、方針変更の制約、成長周期、練習・休養、疲労・モチベーション、失敗やスランプ、重要イベントの分岐と頻度。

**本資料の設計提案**：育成結果には、伸びた能力と関係する方針を簡潔に表示し、プレイヤーが「自分の判断が効いた」と理解できるようにする。表示の具体仕様は未承認。

### 5.5 活動形態・編成・転向

**決定**：自由編成・自由転向。ソロ／バンド／アイドル間の転向、メンバーの追加・脱退、ユニット結成ができる方向。

人材を最初に選んだ活動形態へ永久に固定せず、その人に合う形をプレイヤーが探せることを重視する。

**既出案**：作曲の得意な人物とカリスマ性のある歌手を組み合わせる、メンバー相性によって化学反応を生む。

**未決定**：活動形態ごとの人数、役割、必要能力、同時所属、兼任、掛け持ち、組み替えのコストや期間、相性計算、脱退後の扱い、既存楽曲やファンの引き継ぎ。自由に変更できることと、変更に費用・影響が一切ないことは同義ではない。

### 5.6 楽曲制作

**決定**：初期版は自動制作型。能力・パラメータの成果を楽曲へ反映する。

ユーザーの判断理由は「そのためのパラメータなので」。育成した能力が成果を生む設計を重視している。

**未決定**：制作のきっかけ、制作間隔、制作期間、制作人数、作曲担当の決め方、楽曲属性、品質・ヒットの計算、発売タイミング、曲名、カタログ管理。自動制作は、自動発売や実際の音源生成まで確定した意味ではない。

**将来構想**：必要を感じたら、ジャンル・方向性・制作担当を指定するプロデュース型を追加する。初期版の必須操作にしない。

### 5.7 成果・ランキング

**決定**：ランキングを採用する。

**既出の成果候補**：ファン数、売上、チャート順位、受賞。成功像として、国民的ヒットメーカー、伝説のライブアーティスト、音楽界の巨匠等の案が出ている。これらすべてを初期搭載すると決まったわけではない。

**未決定**：楽曲・アーティスト・事務所の何を順位づけするか、現役／年間／歴代の区分、評価指標、更新頻度、比較対象、ライバルの生成、難易度、報酬。

ランキング採用から、他プレイヤーとのオンライン対戦、サーバーランキング、実在チャートへの接続を推定しない。

**整合性の整理**：初期版でランキングを採用することと、本格的な業界シミュレーションを後回しにすることは両立する。初期ランキングをどこまで簡略化するかは、次の設計で決める。

### 5.8 ライブ・フェス・音楽賞

ライブ動員、フェス実績、音楽賞等は、成果や成功像の例として話題に出ている。**初期版への搭載、操作内容、イベント構造は未決定**。

発掘場所としてのライブハウス、能力としての演奏力、個性としての本番への強さがあるだけでは、ライブ運営システムの採用確定とはならない。

### 5.9 時間進行・プレイ時間・終了

**決定**：経営は当面無期限。**志向**：短時間でも遊びたい。

短いのは一度に遊ぶ時間であり、事務所の存続期間を短く切ることではない、と整理すると両者は両立する。ただし中断・再開の具体的な仕様は未決定。

**既出の時間案**：1プレイ10〜15分、1ターン1年、1シーズン＝1年を約1〜2分で進める、10年間を10〜20分、初期案として1周15〜25分など。いずれも検討中に提示された案であり、確定値として使わない。とくに10年で強制終了する仕様は、その後の無期限方針に優先しない。

**未決定**：1ターンの長さ、年内のフェーズ、早送り、リアル時間連動、放置進行、途中保存、年齢、寿命、引退、破綻、任意終了。

**将来構想**：無期限モードとは別の10年モード。期間を区切る案は残すが、初期版の必須機能ではない。

### 5.10 履歴・蓄積

**決定した方向性**：アーティスト、楽曲、事務所の歴史が蓄積する。

**未決定**：保存する実績、年表、年鑑、殿堂入り、歴代ランキング、過去メンバーの閲覧、楽曲との紐づけ、改名・転向後の記録、保存期間。

**既出案**：年齢やキャリアによる変化、本人の意思やイベントによる引退・独立。これらは検討材料であり、実装確定ではない。

**本資料の設計提案**：現在の状態と過去の出来事を分け、編成変更後も過去の成果の主体を辿れるようにする。これは蓄積型体験と将来の先輩からの楽曲提供を支えるが、データ形式や表示画面は未承認。

## 6. 初期版の範囲と将来構想

### 6.1 初期版で守る中核

発掘二方式、バランス型育成、才能と育成の両立、自由な編成・転向、自動楽曲制作、ランキング、無期限進行、歴史の蓄積を中心に具体化する。これは合意方針の集合であり、工数を見積もった完成済みのMVP仕様ではない。

スコープ調整が必要になっても、合意した中核を黙って削らない。削減・段階導入案は、決定事項との差分が分かる形で示す。

### 6.2 初期版に取り込まず、残す将来構想

| ID | 構想 | ユーザー意向・位置づけ | 後に決めること |
|---|---|---|---|
| F01 | 本格的な音楽業界シミュレーション | ゲームが長くなってもよければ追加 | ライバル事務所、業界動向、競争、音楽賞などの範囲 |
| F02 | 楽曲制作のプロデュース型 | そこもプロデュースしたくなったら追加 | ジャンル・方向性・制作担当の指定、既存自動制作との併用 |
| F03 | 同じ事務所の先輩アーティストからの楽曲提供 | ランダムイベント的にあると面白いが、後回し | 発生条件、先輩の定義、提供先、楽曲の効果、頻度 |
| F04 | 10年モード | 無期限とは別モードにする候補 | 終了時評価、無期限への継続、ランキングの分離 |

F03はユーザーが明示した構想であり、一般的なイベント案に埋もれさせず残す。引退済みの先輩からの提供まで確定しているわけではない。単に同じ事務所の先輩という関係を出発点にする。

### 6.3 未決定と将来構想を混同しない項目

ライブ、フェス、資金、スタッフ、施設、引退、独立、相性システム等は、詳細や初期導入の合意を確認できていない。「初期に入れる」とも「必ず将来へ回す」とも断定しない。

実音源生成、実在アーティスト、マルチプレイ、課金、外部音楽サービス連携についても決定は確認できない。音楽が題材というだけで導入要件にしない。

## 8. 引き継ぎ先向けの実装準備案

**この章はすべて本資料で新たに整理した設計提案であり、承認済み仕様ではない。** コードの実装開始を指示する章でもない。

### 8.1 概念モデル

自由な編成・転向を保つため、個人と活動単位を分けて考える。グループの名称・人数が変わっても、その人物の育成履歴が消えない構造を検討する。

| 概念 | 扱う情報の例 | 関係・注意点 |
|---|---|---|
| 事務所 | 名前、進行時点、所属人物への参照 | 財務は採用を決めてから加える |
| 人物 | ID、現在能力、潜在能力、個性、育成方針 | 活動形態が変わっても同一人物として保持 |
| 活動単位 | ID、ソロ／バンド等の形態、名称 | ソロも一つの活動単位として扱う案 |
| 所属履歴 | 人物、活動単位、加入・離脱時点 | 兼任を許すかは未決定 |
| 楽曲 | ID、制作時点、制作主体、成果 | 制作時の主体を後の編成変更で上書きしない |
| 実績・出来事 | 時点、対象、内容、結果 | 年表や過去の活躍を再現できる形を検討 |
| ランキング記録 | 時点、対象、指標、順位 | 現在順位と過去最高等を混同しない |
| 保存データ | 進行状態、人物・楽曲・記録、形式の版 | 保存方式・移行方式は別途決定 |

個々の能力名、DBやJSONのフィールド、データ型、数式はここでは確定しない。将来機能のためだけに不要な仕組みを先に作り込まない。

### 8.2 画面候補

事務所の概要、発掘候補、所属人物と能力、育成方針・編成、進行結果とイベント、楽曲とランキング、履歴を閲覧する導線が考えられる。これらは機能上のまとまりであり、七つの独立画面に分ける仕様ではない。短時間プレイを重視して統合・簡略化を検討する。

### 8.3 最初に具体化する一本の体験

「人材を見つける→方針を選ぶ→育つ→楽曲が生まれる→結果が残る」までを一度通せる設計案を作り、そこでU01〜U10を詰める。能力の数値を増やす前に、選択と結果の関係を確認する。

### 8.4 検証観点

以下は試作を評価するための観点であり、確定済みのテスト仕様や数値基準ではない。

- 同じ初期人材でも育成方針を変えると、意味のある違いが出るか。
- 人材の適性を見て編成・転向を選ぶ理由があるか。
- オーディションと場所指定スカウトに使い分ける意味があるか。
- 楽曲の成果に能力が反映され、それをプレイヤーが理解できるか。
- ランキングが育成の成果を見届ける喜びにつながるか。
- 一人を贔屓して育てる遊びが成立するか。
- 短い時間でも意味のある判断と結果確認ができるか。
- 編成変更後も過去の楽曲と実績を辿れるか。
- 長く続けても人数、履歴、操作負荷が過大にならないか。

## 9. 整合性と、誤って補完しやすい点

| 論点 | 引き継ぐ解釈 |
|---|---|
| 短時間で遊びたい／経営は無期限 | セッションの長さとゲーム内の存続期間を分ける。固定年数終了へ戻さない |
| 能力重視／才能＋育て方 | 初期能力や潜在能力の良い人を引くだけのゲームにしない |
| 自由編成／バランス調整 | 自由に選べる方針を維持し、コストや影響の詳細は別途検討する |
| プロデュース／楽曲自動制作 | 人材・育成・編成への介入は中核。楽曲ごとの細かな指示は将来候補 |
| ランキング／業界シミュレーション後回し | ランキング採用は維持。本格的なライバル経営や市場計算まで必須にしない |
| 歴史蓄積／引退・独立 | 記録を残す方向性は確定。引退・独立の制度は未決定 |
| 音楽ゲーム／自動楽曲制作 | リズムゲーム操作や実音源の生成を意味しない |
| Web／特定技術 | Webで遊ぶ要件と、使用フレームワーク・バックエンド選定を分ける |
